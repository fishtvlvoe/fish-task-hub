01

dashi-taskboard 原始架構

三種操作介面共用同一組 API，但整套服務只認得「一個 workspace」——沒有跨專案的概念。

02

fish-task-hub 現況：加了單向連結，沒有真正整合

架構骨架沒變，只是在 Ticket 上多接了兩條線：一條讀 SR 文件（唯讀、單向），一條指派給一個 CLI（單選）。

03

目標形態：SR 本身就是卡片，跨專案、多代理、雙向

看板不再依附 Ticket，而是直接以 SR 為單位；一個服務同時涵蓋多個專案；一張卡可以同時指派多個 Agent，各自指定模型；跟 Spectra CLI 的狀態互相同步。

# 要新增的東西 現況
01 SR 自己的一張資料表，欄位對應 proposal／design／tasks／specs 與 PROPOSE–APPLY–REVIEW–DEPLOY–MAINTAIN 狀態 SR 內容仍只活在 openspec/ 資料夾，Ticket 只存一個指回去的 ID
02 服務改成能同時掃描、服務多個專案底下的 openspec/changes/，不再綁死單一 workspace 一個服務實例 = 一個 workspace，換專案要換服務
03 面板操作能真的觸發 Spectra CLI 指令（apply／archive），CLI 執行完狀態也要回寫面板 只有唯讀解析 tasks.md 這一條路，沒有反向的寫入或觸發
04 Worker Adapter 從「一張 Ticket 綁一個」改成陣列，並處理多個 Agent 同時動同一批代碼的衝突（比照這次接力開發用 worktree 隔離的做法） assigneeWorker 是單一欄位，一次只能指派一個 CLI
05 Worker Adapter 的 start() 要加一個「傳入指定模型」的參數，而不是每個 CLI 寫死一套呼叫方式 CodexAdapter／CursorAdapter 目前都用各自 CLI 的預設模型，沒有可調參數
